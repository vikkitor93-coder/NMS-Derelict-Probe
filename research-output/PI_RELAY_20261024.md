## Behaviour (as built)

- **Allowlist:** `GET /api/health` (query dropped) and `GET /api/map/<16 hex>[?wait=S]` only. Validation reproduces the server: 16 hex
  (`400 bad_address`), the server's `000 SSS 00 YYZZZXXX` regex (galaxy byte other than 00 gives `400 galaxy`; system 000 gives `404 no_such_system`),
  `wait` a plain number (`400 bad_wait`), capped at 90, path at most 200 chars. The address is upper-cased; only a re-built `?wait=` is
  forwarded, never the client's query. Everything else 404; POST/PUT/DELETE/PATCH 405; request bodies 400; OPTIONS answered locally.
  A unit test compares every error message with the text in `ondemand_server.py`.
- **Polling endpoint:** none exists in the server file yet (last modified 01:25; the ETA agent's 02:30 NOTICE is still open, no DONE). Polling is the same
  `/api/map/<addr>?wait=` URL and 202 answers pass through untouched. If a new route appears, add one `if` block to `route()` in `relay.py` and a test.
- **Upstream:** config `upstream_host` (default the Tailscale IP `100.x.x.x`; `HOSTNAME` works if MagicDNS resolves it) + port. It is resolved
  (cached 30 s) and **only a 100.64.0.0/10, fd7a:115c:a1e0::/48 or loopback address is ever connected to**; anything else counts as offline.
- **Origin / CORS:** the relay checks the Origin with the server's rule (configured list plus localhost/127.0.0.1) and answers 403 without CORS
  headers for others; the original Origin is passed through to the PC unchanged. The CORS header of the PC's answer is not copied; the relay
  sets `Access-Control-Allow-Origin` itself (same value) on every answer, including 404/405/429/offline. `Accept-Encoding: gzip` is
  passed on and the gzip bytes come back untouched.
- **Client address:** `X-Forwarded-For` is honoured **only when the TCP peer is loopback** (Funnel's local proxy), using its last entry
  (the one our proxy appended; a visitor-supplied prefix is ignored); IPv6 is grouped by /64. It becomes `HMAC-SHA256(random per-start salt, ip)`
  (18 hex chars), used for the in-memory sliding-window limiter (120/min) and sent to the PC as `X-Relay-Client`. The raw address is never
  forwarded, logged or written; a test checks that the stats file holds none of the test addresses, user agents or map addresses. If the
  proxy sends no `X-Forwarded-For`, all visitors share one bucket; that is counted as `no_client_header` on the page so it can be noticed.
- **Offline:** connect timeout 2 s (read timeout 15 s plus `wait`). On connect failure the relay answers **HTTP 502**
  `{"status":"offline","message":"Map server offline, try later"}` with CORS and `Retry-After: 5`. 502 is deliberate: the site client
  (`ondemand.js`) treats 503 as "busy" and any status other than 200/202/400/404/429/503 as "Map server offline, try later." For the next 5 s every request
  gets that answer immediately, then one probe. PC answers with other statuses are turned into the same offline answer.
- **Health cache:** 5 s, single-flight (12 concurrent requests make 1 PC call), only 200s are cached. **No map data is cached.**
- **Logs/stats:** no access log. Per UTC day counts in `~/.local/share/nms-traffic/relay.sqlite` (`relay_daily`: requests, forwarded,
  health_cache_hits, map_200/202, offline, not_found, bad_request, method_not_allowed, rate_limited, origin_rejected, forbidden, busy,
  upstream_error, upstream_refused, conn_refused, no_client_header, handler_error), flushed each minute, plus a totals line to the journal every 10 minutes.

## PC-side change (NOT done; needed before the relay can reach the PC)

`ondemand_server.py` hard-binds `127.0.0.1` (`cfg["host"] = "127.0.0.1"` in `load_config`, "never anything else"), so a tailnet client gets
"connection refused". The ETA agent's 02:30 NOTICE is open on that file, so I did not touch it. After its DONE (or with a NOTICE):

1. **Second listener on the PC's Tailscale IP.** New config keys `tailnet_bind` (default `""` = off; e.g. `"100.x.x.x"`) and `relay_ips`
   (list; the Pi's tailnet IP). In `serve()` start a second `AppServer` bound to `(tailnet_bind, port)` that shares the engine, stats and limiters, and in its
   `process_request` close any peer not in `relay_ips`. The loopback listener stays as it is.
2. **Trust `X-Relay-Client` only from the relay.** In `Handler.client_key`: if `peer in cfg["relay_ips"]` and the header matches `^[0-9a-f]{18}$`,
   use it as the IP string (still salted-hashed, memory only); otherwise unchanged. Never trust it from loopback or other peers (the existing
   `CF-Connecting-IP` / `X-Forwarded-For` logic for loopback stays).
3. **Windows firewall** (admin PowerShell): `New-NetFirewallRule -DisplayName "NMS on-demand (Pi relay only)" -Direction Inbound -Protocol TCP -LocalPort 8791 -RemoteAddress <Pi tailnet IP> -InterfaceAlias Tailscale -Action Allow`.
   A Tailscale ACL limiting `HOSTNAME:8791` to the Pi is a good second lock.
4. CORS needs no change (the relay passes the Origin; the server already allows the public site). `clients_1min` on `/api/health` will then count relay keys.

Until then the path over the tailnet is untested; the relay-to-server HTTP path was tested on loopback (below).
